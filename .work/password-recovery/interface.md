# interface — F1.6 password-recovery, part a (server and database), with Amendment 2

Facts only. Web (part c) is not built yet: no screen, no accessible name.

## HTTP

All JSON. All three recovery answers carry `cache-control: no-store`. A body over 16 KiB (`RECOVERY_BODY_LIMIT_BYTES`) is refused before parsing. A malformed JSON body, an unsupported content type or an oversize body: 4xx `{"error":"bad_request"}`. A `text/plain` body is parsed by Fastify as a string and then fails the route's schema: 400 with the route's own validation code (`invalid_request` on reset, `invalid_questions` on the questions routes), uncounted — the same as `/api/register` (ORCHESTRATOR, 15.10, step 2 of the handoff).

| Route | Auth | Body (strict objects, no other key) | Answers |
|---|---|---|---|
| `POST /api/recovery-questions` | Bearer, protected | `{"answers":[{"question","answer"},{"question","answer"}]}` | 201 `{"ok":true}` · 400 `{"error":"invalid_questions"}` · 409 `{"error":"already_set"}` (checked BEFORE the new pair is hashed: no scrypt call) · 403 `{"error":"forbidden"}` (database policy refused: account not active, or no account row) · 503 `{"error":"unavailable"}` (pepper missing, transient database fault, or another account holds the token's email under a claim that is not older: stale token, nothing changed) · 500 `{"error":"internal"}` (token without an email claim or without `iat`, other faults) · 401 from the hook |
| `PUT /api/recovery-questions` | Bearer, protected | `{"current":[2 entries],"answers":[2 entries]}` | 200 `{"ok":true}` · 400 `invalid_questions` · 401 `{"error":"invalid_recovery"}` (wrong current pair, counted) · 409 `{"error":"not_set"}` (no answers row visible to the caller: none saved, OR the account is not active, because `recovery_answers_select_own` hides the row of a suspended or banned account; there is no 403 on this route for that case) · 429 `{"error":"rate_limited"}` + `retry-after` (seconds) · 403 (a policy refusal on the write) · 503 `unavailable` (also: the own handle is stale or released and could not be re-keyed to the token's email) · 500 · 401 `unauthenticated` from the hook. The new pair is hashed only after the current pair matched (a 401, 429 or 409 costs no new-pair scrypt) |
| `POST /api/recovery/reset` | **public** (in `PUBLIC_ROUTES`) | `{"email","answers":[2 entries],"password"}` | 200 `{"ok":true}` · 400 `{"error":"invalid_request"}` (before any lookup, uncounted) · 401 `{"error":"invalid_recovery"}` (every failure to prove the answers, identical) · 429 `rate_limited` + `retry-after` · 503 `{"error":"unavailable"}` (pepper or Auth key/issuer missing, before database work; Auth read-email or set-password or global sign-out not confirmed; transient database fault) · 500 `internal`. A verified reset whose account's CURRENT Auth email is not the request's email is 401 `invalid_recovery` (same body as a wrong answer), no password set, no sign-in or sign-out call |
| other methods on both paths | | | 405 `{"error":"method_not_allowed"}` with `allow: POST, PUT` (questions) or `allow: POST` (reset); the hook answers 401 first when not signed in |

Entry: `{"question": "pet"|"nickname"|"street", "answer": string}`. Exactly two entries, two different ids. Answer: at most 600 UTF-16 units raw; 2 to 60 code points after normalising (`normalizeRecoveryAnswer`). Email: VAL-002 (trimmed). Password: VAL-003 (8 to 256 code points, not trimmed).

`GET /api/me`: `active` gives `{"state":"active","recoveryQuestions":"set"|"missing"}` (exactly those two keys); `unavailable` and `unregistered` give `{"state":...}` only. After the state is read, for an `active` account with a row, when the pepper is set and the token has an email and `iat`: if H(token email) differs from the row's `email_handle` (or it is NULL) and the row's `handle_claimed_at` is NULL or older than the token's `iat`, a SEPARATE transaction re-keys the row (event `handle_rekeyed`; an older holder of that handle is released first, event `handle_released`). The body is the same whether the re-key happens, fails (one `warn` line `recovery handle re-key failed` with `sqlstate`) or is skipped. The route awaits the re-key before replying.

Client address: `request.ip` with Fastify `trustProxy` as a function trusting the socket hop only, i.e. the last `X-Forwarded-For` entry. A test sets `x-forwarded-for` to choose the address. IPv6 is counted by its /64; `::ffff:a.b.c.d` as IPv4. A non-address counts under the single key `unknown`.

## Test seams and how to drive

- Pepper: set env `RECOVERY_PEPPER` (32+ random bytes, base64) before the request, or pass `recovery: { keys: () => ... }`. Missing/short gives 503 on the three endpoints.
- Scrypt spy: `recovery: { scrypt: spy }`; each failing or verified attempt that reaches verification calls it exactly twice (the limited path calls it zero times). A store hashes the new pair (two calls) only when the account has no answers yet; a change hashes the new pair (two more calls) only after the current pair matched. Both happen inside the transaction.
- Auth stand-in: either `recovery: { authAdmin: { isConfigured: () => true, resetPassword: async () => 'completed' | 'admin_failed' | 'revoke_failed' | 'email_mismatch' } }`, or a local HTTP stub with env `SUPABASE_JWT_ISSUER=http://127.0.0.1:<port>/auth/v1` and `SUPABASE_SECRET_KEY=<any>`; the stub sees the four requests above in order (the first is a GET returning a JSON body with `email`).
- Database: real `DATABASE_URL` as `app_server` (tests/db). Roles `authenticated`, `app_recovery` and the migration `20261015200000_recovery_questions.sql` must be applied. Database clock decides windows and locks: a test moves state with SQL on `nestly.recovery_throttles` as the owner (e.g. set `locked_until` or window starts into the past), not with an app clock.
- A request's tokens: verified ES256 token as before; the store route needs an `email` claim and an `iat` (the test fixtures already put `iat` in every token); `iat` orders two claims to one email (later wins, strictly: an equal `iat` does not release). To make a token stale, sign one with an earlier `iat`.
- Logs (`logStream`): the request line carries `{method, url}` where `url` is the route pattern (`unmatched` for no route). Fixed error lines: `recovery request failed`, `recovery reset failed`, `recovery answers write failed`, `recovery answers change failed`, `recovery reset: the outcome row was not written`, `recovery questions: the token has no email claim or issue time`, `recovery questions: the email handle is held by a newer claim` (warn), `recovery questions: the email handle could not be re-keyed` (warn), `recovery handle re-key failed` (warn, from /api/me); fields `status`, `code`, `sqlstate` only.

## Database (pgTAP targets)

- Tables `nestly.recovery_answers`, `nestly.recovery_throttles`, `nestly.recovery_events`; helpers `nestly.recovery_handle()`, `nestly.recovery_ip()`, `nestly.recovery_claimed_at()` (timestamptz, from `nestly.recovery_claimed_at`); role `app_recovery` (bootstrap step 1).
- 9 policies (the new one is `recovery_answers_release_recovery`, FOR UPDATE TO app_recovery: USING `email_handle = recovery_handle() and handle_claimed_at < recovery_claimed_at()`, WITH CHECK `email_handle is null and handle_claimed_at is null`): `recovery_answers_select_own`, `_insert_own`, `_update_own` (authenticated); `recovery_answers_select_recovery`; `recovery_throttles_select_recovery`, `_insert_recovery`, `_update_recovery`; `recovery_events_insert_recovery` (all app_recovery).
- Declaring in a test transaction: `set local role app_recovery; select set_config('nestly.recovery_handle', '<64 hex>', true), set_config('nestly.recovery_ip', '<64 hex>', true), set_config('nestly.recovery_claimed_at', '<iso timestamp or empty>', true);`.
- `recovery_answers`: `email_handle` is now NULLABLE and there is a new column `handle_claimed_at timestamptz` (CHECK `recovery_answers_handle_claim_check`: both NULL or both set). Every INSERT of an answers row must give both. `authenticated`: SELECT adds `handle_claimed_at`, INSERT adds `handle_claimed_at`, UPDATE adds `email_handle` and `handle_claimed_at` (own row, `recovery_answers_update_own`). `app_recovery`: UPDATE on `(email_handle, handle_claimed_at)` only (through the release policy).
- The release statement the server uses, as `app_recovery`, with the handle and claim time declared: `select user_id from nestly.recovery_answers for update` (no `where`) returns the holder exactly when its claim is older; then `update nestly.recovery_answers set email_handle = null, handle_claimed_at = null` with NO `where` and NO `returning` (either would fail on the SELECT policy). The `handle_released` event must be inserted BEFORE it.
- `recovery_throttles`: new column `limited_noted_until timestamptz` (granted to `app_recovery` for UPDATE): the `locked_until` value for which a limited event was written. `recovery_events.kind` gains `reset_email_mismatch`, `handle_released`, `handle_rekeyed` (user_id not null for all three).
- Limited events: while an IP is locked, no `recovery_throttles` row is created for the submitted email, and one `reset_limited` / `change_limited` row is written per subject per lock (the first limited attempt; later ones write nothing). A locked handle (IP not locked) does the same with the handle row. Retry-after is that of the locked subject that stopped the request (the IP's when the IP is locked). Lock order is IP row first, then handle row, on every path. After a mismatch the failure is counted on the IP, then on the handle.
- Constraint names: `recovery_answers_pkey` (a second save, 23505), `recovery_answers_email_handle_key` (23505 here on a store or re-key means the holder's claim is not older), `recovery_answers_handle_claim_check`, `recovery_answers_question_order_check`, `recovery_answers_salts_differ_check`, `recovery_answers_scrypt_log_n_check`, `recovery_events_kind_check`, `recovery_events_user_id_check`, `recovery_throttles_long_window_check`, `recovery_throttles_long_failures_check`.
- Down script: `supabase/rollback/20261015200000_recovery_questions.down.sql` refuses while `recovery_answers` or `recovery_events` holds a row.
