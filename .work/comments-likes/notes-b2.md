# notes — F3.3 b2 likes server + counts

**Approach**        New `likes-repository` (counts, `likedByMe`, write), `likes-service`, `routes/likes` (PUT/DELETE `/api/posts|comments/:id/like` → 204). Counts and `likedByMe` are added after ranking/display in the feed, `GET /api/posts/:id`, thread, replies and create-comment. `inIdentityTransaction` takes an option `isolationLevel: 'repeatable read'` (runs `set transaction isolation level repeatable read` before the role/guard statement); used by feed page, post read, thread, replies.
**Decisions**       All new SQL is in `likes-repository.ts`, not `feed*.ts` (the static test forbids `reaction_owners` there). Idempotent PUT: the second insert hits the one-like UNIQUE (23505) inside a savepoint and returns normally. DELETE is `delete from reactions where target_id = $id`; the delete policy limits it to the caller's own. Readability checked first (404). `commentCount` counts a reply only if its parent row is readable (`exists` on comments under RLS). Comment view carries `likeCount` + `likedByMe` only (a comment has `replyCount`; no `commentCount`). `postReadView` (GET only) gets the three keys; `postView` (POST/PATCH) unchanged. Create-comment response also carries the two like keys.
**Deviations**      Web touched minimally for typecheck: three story fixtures and `PostScreen` (edit keeps the counts from the read). No behaviour change.
**Deliberately not done**   No web UI (w1/w2). No test edits.
**Uncertain**       `commentCount` on a comment view (spec text says "three keys" to comment view; I read it as the two that apply). Prettier was run with single quotes/width 150, so a few unrelated lines in comments/posts services were reflowed.
