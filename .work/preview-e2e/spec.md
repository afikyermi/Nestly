# E - Automated Preview E2E

**Problem**        Afik checks every Preview by hand against a checklist (F1.6 is the case at hand). Nothing exercises the real Supabase Auth, the real server and the deployed web app together before merge, so Gate 3 depends on a person.
**Requirements**   Not a product feature: no FR. Source `.work/preview-e2e/intake.md`; decisions/2026-10.md "Development speed" (E). It walks F1.6's flow, whose criteria 16-18 and 9 are in `.work/password-recovery/spec.md`. SRS trace in `result.md`: NFR-QA-001 / OP-018 (Playwright, Chrome). Behaviour beyond those: flagged below.
**Scope**          A workflow `preview-e2e` triggered by a successful Vercel Preview deployment; job in GitHub environment `preview-e2e`; refusal guards; a test-user lifecycle (create, cleanup, sweep); the F1.6 flow at 375 and desktop on Chrome; a result on the commit; a folder where each later feature adds one flow file. Lives on `feat/f1-6-password-recovery` (PR 31).
**Out of scope**   Production (any URL, key, project, DB); Edge and Firefox; visual-regression baselines; flows for features other than F1.6; replacing `preview-smoke` (it stays unchanged and separate); a merge of PR 31 or any push to main; storing videos or traces (they could capture credentials); the deletion SQL/order and the roles (DATA ARCHITECT, `.work/preview-e2e/schema.md`); creating the secrets (Afik enters them).
**Data touched**   nestly-preview only (`xmihorrkegrdlbhpktny`): Auth users and every row tied to them, created and deleted by the job. No schema change. Deletion order/SQL: schema.md (reference, not designed here). **Risk flags** a new deletion-capable credential in CI; a destructive operation on the preview DB; authentication (real accounts, recovery).

**Acceptance criteria**
1. 🔴 Trigger: the job's `if` runs only for `deployment_status` with state `success`, environment `Preview`, creator `vercel[bot]`. A workflow-lint test over fixture events asserts it runs for that event and not for: state `failure`/`pending`, environment `Production`, creator `someone-else`. No other trigger (no `pull_request`, `workflow_dispatch`, `schedule`); `permissions: contents: read` plus whatever the commit result (criterion 10) needs, nothing broader.
2. 🔴 The job declares `environment: preview-e2e`. The three secrets (`PREVIEW_SUPABASE_SECRET_KEY`, `PREVIEW_DB_ADMIN_URL`, `VERCEL_AUTOMATION_BYPASS_SECRET`) appear in `env` only of the steps that use them, never at workflow or job level. The workflow file contains no `${{ secrets.* }}` inside a `run:` body and no `${{ github.event.* }}` inside a `run:` body (values arrive through `env`); a lint test asserts this on the YAML.
3. 🔴 Refusal before any connection: a guard (unit-tested like `tools/migrate-url-guard.mjs`, exit 1, a reason naming only what was expected) runs first and stops the job when any of these fails. Deployment URL not `https://nestly-<hash>-afikyermis-projects.vercel.app` (same rule as preview-smoke; a branch alias, port, path, user or other host refused). DB URL not user `postgres.xmihorrkegrdlbhpktny`, a `*.pooler.supabase.com` host, port 5432, sslmode absent/`require`/`verify-full`, no `#`, no other query key. Secret key not for `xmihorrkegrdlbhpktny` (see QUESTION 1). Unit cases: the prod ref `cihugbwafnaujsqabgyp`, an empty value and a look-alike host are each refused; no network call is made by the guard (a test with the network stubbed to throw).
4. 🔴 Secrets never leak, asserted by a test that runs the flow and cleanup against a local fake Supabase/Vercel with sentinel secret values: no sentinel in stdout/stderr, in the Playwright report, in any file the job uploads, or in any process argv; none in a URL or query string. The bypass secret goes only to the deployment host (header `x-vercel-protection-bypass`, or the `x-vercel-set-bypass-cookie` as in `tools/preview-shot.mjs`); the secret key only to `https://xmihorrkegrdlbhpktny.supabase.co`; the DB URL only to its pooler host. The fake records every request's host: a sentinel seen at any other host fails the test. Redirects are not followed with a credential (cross-host redirect = failure).
5. 🔴 Each Playwright project (viewport) creates its own user: email `e2e-preview-<GITHUB_RUN_ID>-<project>-<8 random hex>@example.test` (domain per QUESTION 2), random password of at least 16 characters, random answers; values are distinct between the two projects and between two runs; the email pattern is one exported constant with an anchored regex, used by creation, cleanup and sweep. A unit test asserts the generated email matches the regex and that `alice@example.com` and `e2e-preview-1-x@example.test.evil.com` do not. The password and answers are never logged.
6. 🎨 F1.6 flow at 375x812 and at 1280x800 on Chrome, each against the Preview URL with real Auth: (1) sign up opens the questions screen at once; navigating to `/feed` and a reload both return to it; (2) choose 2 of 3, answer, "שמירה" lands on `/feed`; (3) log out, sign in: no questions screen; (4) menu "שאלות לשחזור סיסמה": wrong current answers show the mismatch text, correct ones show a confirmation; (5) log out, `/recovery` with email, both answers and a new password shows success; (6) sign in with the new password reaches `/feed`, and the old password gets the invalid-credentials text. Each step asserts a visible Hebrew heading/text or URL, not only absence of error. Spec traces: F1.6 criteria 16-18, 9.
7. 🎨 F1.6 negative path in the same run at both viewports: `/recovery` with a wrong answer shows the single mismatch text and the new-password field is empty afterwards; the run uses the user's own email only, never another's. No test submits more than 4 failed recovery attempts per user and the failed attempts stay under F1.6's 5-per-30-minutes limit (criterion 12), asserted by a counter in the helper that throws on the 5th.
8. 🔴 Cleanup in all outcomes: a separate step with `if: always()` (also after the test step is cancelled by its own `timeout-minutes`, which is smaller than the job's so cleanup still has time) deletes the users it created, via the Auth admin API and the deletion in schema.md, and fails the job if any remains. Test, with a fake: flow passes, flow throws, test step timeout - each leaves zero users matching the pattern and zero rows tied to them (the row list is from schema.md). A cleanup error is reported as a failure of the job even when the flow passed.
9. 🔴 Sweep: the same step also deletes users matching the anchored pattern left by earlier runs, and only those: a decoy user not matching the pattern (including one matching a prefix only) survives, asserted in a test. It skips matches created in the last 30 minutes, so a concurrent run's live user is not deleted; the workflow has `concurrency: preview-e2e` with `cancel-in-progress: false`. If more than 50 users match, nothing is deleted and the job fails (a wrong pattern must not wipe the project).
10. 🟡 The result is on the commit: the job posts a check run named `preview-e2e` on the deployment's `sha` with conclusion `success` or `failure` (never left `in_progress`/missing after a guard refusal, a flow failure or a cleanup failure). Asserted by `gh api repos/<repo>/commits/<sha>/check-runs` in the first real run, and by a test that the final step runs `if: always()`. Its summary lists steps passed/failed per viewport, with no user data beyond the run id.
11. 🟡 Extensibility: flows live one file per feature in `e2e-preview/` (`e2e-preview/<feature>.flow.ts`, exact name builder's), each exporting a flow that receives the generated user and the Preview URL; the workflow and config discover files by glob. Test: adding a fixture flow file runs it at both viewports with no edit to the workflow; a flow file cannot read the three secrets (they are not in the Playwright process env; only the generated user and base URL are). A short `e2e-preview/README.md` (at most 15 lines) states the rule.
12. 🟡 Playwright config is separate from the Storybook/local one: `npm run e2e` and CI's existing e2e job never run `e2e-preview/`, and the Preview job never runs `e2e/`; the base URL comes from the validated deployment URL only, with `retries: 0` (a retry would create another user and mask a flake) and per-test timeout of at most 90 s. Asserted by config tests.

  `fetch` and the DB client stubbed. Each test records the destination host and the args and checks them against the

  the test step's `timeout-minutes` < the job's. "Zero users and zero rows remain" is asserted by the real run itself:
  the cleanup step's final query counts users matching the pattern and fails on > 0.
- A3 (criterion 10 / QUESTION 3): no extra permission first. The workflow run's own check on the deployment `sha` is the
  result, and the first real run confirms it shows on PR 31 (`gh pr checks`). Only if it does not show,
  `statuses: write` and a commit status `preview-e2e` are added.
