# F1.8 google-sign-in

**Problem**        A parent who wants to start or come back with their Google account cannot: Welcome, Login and Register offer only email and password, and `/auth/google` is a placeholder.
**Requirements**   FR-AUTH-005 (`05-functional/auth.md:61`) · AC-087 · FR-AUTH-002 status checks (AC-099, AC-100, AC-101, NFR-SEC-009) · FR-REG-002/-004 (`registration.md`, AC-088) · VAL-003 · BR-045 · ERR-001 · §12 External Login. Not in the SRS: the guard exception (Afik 17.10) and Gate 3 from `preview-e2e` (E); the Google-user password (Afik 17.10, new requirement, replaces "בלי סיסמה" in FR-AUTH-005 / FR-REG-004; SRS at I1 close); DR-5. All in `decisions/2026-10.md`.
**Scope**          Three parts, in order. **P1 guard (built, unchanged):** the TEST ENGINEER test-file rule learns `e2e-preview/*.flow.ts`. **P2 auth core (Elevated; flags: auth, personal data, new provider, unauthenticated return URL):** Google start and return in the Auth client, the return route `/auth/google` (existing Guest path) with its failure states, clearing Google's profile keys, and the F1.5 completion mode for a Google user with no account, extended with step 2 (password, consent + 18+) and the password set. **P3 screens (Standard):** the button on Welcome, Login, Register step 1; flow file `e2e-preview/google-sign-in.flow.ts`. No server change.
**Out of scope**   Rule L (identity-linking defence, unlink, server refusal of OAuth tokens): not built, Afik 17.10. Supabase links a Google sign-in to an existing account with the same email automatically; the pre-account takeover risk is accepted and listed in `security-privacy-open.md` (S-01) for treatment before launch. Also out: "connect Google" in Settings; unlinking; Apple or other providers; Google logo asset (text button); prefilling name from Google; showing Google's name or picture anywhere; Turnstile (I9); email verification; production setup; a password field for an email+password orphan (F1.5 completion, unchanged); a stored sign-in method; editing the SRS (once per Initiative); any server route, middleware or token-verification change; any other guard rule, agent, skill or setting.
**Data touched**   No product table. Auth side only: `auth.users` / `auth.identities` rows for a Google user; the Auth user's password set by the client; `user_metadata` Google keys cleared. Supabase's identities table keeps Google's identity data (accepted, DR-5). Expected no migration; if DATA ARCHITECT finds one needed it returns as MATERIAL CHANGE and Gate 2.

**Acceptance criteria** (🔴 security/data · 🎨 UI · 🟡 logic)
1. 🔴 P1. For role TEST ENGINEER the guard allows a write to `e2e-preview/google-sign-in.flow.ts` and any `e2e-preview/<name>.flow.ts`, and denies `e2e-preview/support/test-user.ts`, `e2e-preview/playwright.config.ts`, `e2e-preview/a.flow.ts.bak`, `e2e-preview/sub/a.flow.ts`, `x/e2e-preview/a.flow.ts`, `apps/web/src/a.flow.ts`. Guard unit test per path.
2. 🔴 P1. Every path denied for any role before the change stays denied, and BUILDER/CRITIC gain no allowance (existing guard tests unchanged and green); the PR's changed files outside P2/P3 are the guard rule and its test only.
3. 🔴 P2. The failure text is identical (same DOM text, same URL state) for: a provider error, a missing or reused `code`, a failed code exchange, and Auth not configured. Text (Hebrew, `ux-copy-he`): "לא הצלחנו להשלים את הכניסה עם Google. אפשר לנסות שוב, או להתחבר עם אימייל וסיסמה." It contains no provider `error_description`, no email.
4. 🔴 P2. Cancelled consent (`/auth/google?error=access_denied`) shows "הכניסה עם Google בוטלה. אפשר לנסות שוב, או להתחבר עם אימייל וסיסמה." and creates no session. `?error=server_error&error_description=<img src=x>` shows the criterion 3 text and the description appears nowhere in the DOM.
5. 🔴 P2. After the route handles a return, `code` and `error*` are gone from the address bar and history (replace); opening the same URL again yields the criterion 3 text and no session. Every failure screen has a link to `/login` and one to `/register`.
6. 🔴 P2. Google user with an active account → session, then `/feed` (AC-087); status suspended or banned → session ended, ERR-037 text, no protected screen (AC-099); scheduled for deletion → the F1.5 path (PG-050). The same session-source status check as for password runs; no second implementation.
7. 🔴 P2. Google Auth user with no account → `/register` in completion mode (AC-100): step 1 with name, birth date and other fields empty (nothing prefilled from Google), then step 2 with a password field (VAL-003, the same rules, error copy and show/hide control as the email path) and the consent + 18+ checkbox (AC-088). Final action "יצירת חשבון" is disabled until password is valid and the checkbox ticked. Fake-port test per field.
8. 🔴 P2. Ordering. The final action calls `updateUser({ password })` first and sends the existing `POST /api/register` only after it resolves; the register body contains no password. If `updateUser` fails, register is not sent, the user stays in completion on step 2 with the generic error text, and the form keeps its values except the password. Fake-port test asserts call order and both cases.
9. 🔴 P2. If `POST /api/register` fails (any 4xx/5xx or network), the user stays in completion with the error shown; retrying calls `updateUser({ password })` again and then register; on the retry a `same_password` error from `updateUser` counts as success (Supabase refuses an unchanged password, `internal/api/user.go`). The password is never in web storage, a URL, a log or the console (sentinel test).
10. 🔴 P2. In completion the email is the one on the Auth user (Google's), shown read-only (not an editable input; value not sent in the body if the register contract takes it from the token) and no email input exists. For an email+password orphan (F1.5 completion) there is no password field and no `updateUser({ password })` call: existing F1.5 tests unchanged and green.
11. 🔴 P2. Until the account exists, every protected route (`/feed`, `/settings`, a sample of each guard class) redirects a Google user without an account to `/register` completion; a Google user whose register failed is redirected back on reload. Existing access-decision test extended with this state.
12. 🔴 P2. DR-5. After a Google return the client clears Google's profile keys from the Auth user's `user_metadata` (the keys Supabase's Google provider fills: `full_name`, `name`, `avatar_url`, `picture`, plus any other it adds) before the first screen after the return renders, and nothing in `apps/web/src` reads them: the source scan finds no read of those names, and the only occurrence is the one clearing function's list. Fake-port test: given metadata with the keys, `updateUser` is called to clear them; given none, no call; a failed clear does not block sign-in and is not shown.
13. 🔴 P2. Personal data: the start call asks Google for `openid email` only (if Supabase refuses that, DR-3); after a Google return web storage holds only the one session key (tokens, no email, NFR-SEC-009/AC-101); nothing from the identity is sent to the server except the access token.
14. 🔴 P2. Guest-only: `/auth/google` is reachable signed out; signed in, it redirects to the landing page without exchanging a code; `/auth/google/extra` stays denied (existing access-decision test); no new route in the server's route list and no server file changed; no new endpoint creates a `nestly.users` row (completion uses the one register route, so Turnstile in I9 covers it).
15. 🟡 P2. The Google start does not log or place the PKCE verifier, code or tokens in any URL other than the provider's `redirect_to`, console or storage other than the SDK's own session key; leak test with sentinels like the existing source scans.
16. 🎨 P3. "המשך עם Google" is a button on Welcome, Login and Register step 1 (not on step 2, consent or completion), named exactly so, Enter and Space activation, 44px target at 375, RTL order intact, axe clean at 375 and 1280.
17. 🎨 P3. Pressed, the button is disabled and `aria-busy` until the browser leaves; a double press starts one authorize navigation; with Auth not configured the criterion 3 text appears inline and no navigation happens.
18. 🎨 P3. The return screen shows a heading and the text in a `role="alert"`, moves focus to the heading, passes axe at 375 and 1280, and the placeholder title is gone. Completion step 2 for a Google user passes axe at 375 and 1280, the password field has a label and error text linked by `aria-describedby`.
19. 🟡 P3. `e2e-preview/google-sign-in.flow.ts` at 375x812 and 1280x800 on Chrome (Gate 3 automated part): on each of three screens the button, pressed, requests `https://xmihorrkegrdlbhpktny.supabase.co/auth/v1/authorize` with `provider=google` and `redirect_to` = the Preview origin + `/auth/google` (request intercepted and aborted, no Google page loaded); the return URLs of criteria 3, 4, 5 show the exact texts and leave no session key in localStorage. No real Google credentials.

**Manual checks (Afik, on the final Preview, stated as manual)** (a) a new Google user: step 1, step 2 with a password, consent, account created, F1.6 gate; (b) after (a), sign out and sign in with that email and password; (c) a new Google user who closes the tab before the final action returns to completion on every protected URL; (d) Supabase Users page: that user's `user_metadata` shows the Google name/picture keys cleared (criterion 12); (e) a returning Google user to `/feed`; (f) cancelled consent.
