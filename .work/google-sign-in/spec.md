# F1.8 google-sign-in

**Problem**        A parent who would rather not create a password cannot join or come back: Welcome, Login and Register offer only email and password, and `/auth/google` is a placeholder.
**Requirements**   FR-AUTH-005 (`05-functional/auth.md:61`) · AC-087 · FR-AUTH-002 status checks (AC-099, AC-100, AC-101, NFR-SEC-009) · FR-REG-002/-004 (`registration.md`, AC-088) · BR-045 · ERR-001 · §12 External Login. Not in the SRS: the guard exception (Afik 17.10, `decisions/2026-10.md`) and Gate 3 from `preview-e2e` (E), both flagged below.
**Scope**          Three parts, in order. **P1 guard (Elevated):** the TEST ENGINEER test-file rule learns `e2e-preview/*.flow.ts`. **P2 auth core (Elevated; flags: auth, personal data, new provider, unauthenticated return URL):** Google start and return in the Auth client, the linking rule, the return route `/auth/google` (existing Guest path, reused) with its failure states, reuse of the F1.5 completion mode for a new user, and the server refusal of an OAuth token on an email-identity user (in token verification, `apps/server/src/lib/token-verifier.ts`, answered by `plugins/authentication.ts`). **P3 screens (Standard, no flag):** the button on Welcome, Login, Register step 1; flow file `e2e-preview/google-sign-in.flow.ts`.
**Out of scope**   Linking Google to a password account (a "connect Google" action in Settings; the proof would be the password); unlinking; Apple or other providers; Google logo asset (text button); prefilling name from Google; Turnstile (I9, below); email verification; production setup; recovery-question rules for Google users (DR-2); a stored sign-in method; editing the SRS (once per Initiative); changes to any other guard rule, agent, skill or setting.
**Data touched**   No product table. Auth side only: `auth.users` / `auth.identities` rows for a Google user. The server reads two claims (`amr`, `app_metadata.providers`) of the already verified JWT, only to refuse; nothing is stored or passed to the database. Expected no migration; if DATA ARCHITECT finds one needed it returns as MATERIAL CHANGE and Gate 2.

**Rule L (identity linking)** A Google sign-in never ends in a working session on, nor leaves a Google identity attached to, an Auth user that already has an **email identity** (password) for that address, whether or not that user has an account. Why: emails are not verified at sign-up (AC-091), so Supabase treats the auto-confirmed email identity as verified and, with automatic linking, would attach Google to an account an attacker may have pre-created with the victim's address (pre-account takeover, who keeps the password). Enforced twice (DR-1, decided): the client return route detects, unlinks and signs out (criterion 3); the server refuses the OAuth token (criterion 4). No Supabase setting is relied on; "Confirm email" stays off. A Google-only Auth user (no account) is not blocked: they sign in again and continue to completion.
