## P2a — Google start, return route, failures, status, metadata clear (criteria 3-6, 12-15)

**Approach**        `services/auth/auth-client.ts`: new `GoogleAuthPort` (`startGoogleSignIn(redirectTo)`, `completeGoogleSignIn(code)`) on `BrowserAuthPort`. Start = `signInWithOAuth` with `skipBrowserRedirect`, scopes `openid email`, returns the URL; nothing navigates here (the P3 button needs a `platform/` navigation adapter). Return = `exchangeCodeForSession`, then `updateUser({ data })` nulling the Google profile keys that are present (list: one const, the only place they are named); a failed clear is swallowed on purpose (spec c12). Session source: `signInWithPassword` body became `signInThrough(obtain)`, so the password and the Google return share the one status check; `SessionAccount.signInWithGoogle(code)`. Route `/auth/google` = `features/google-return/GoogleReturn.tsx` (+ `google-return.ts` texts and the address reader, `pages/google-return`). It snapshots the address, replaces it with the bare path at once, then exchanges; every failure is one text, `access_denied` has its own, stopped = ERR-037 text. `STOPPED_TEXT` moved from `features/login` to `lib/auth-texts.ts` (a Feature may not import a Feature).
**Decisions**       (1) PKCE is switched on per call (`NestlyGoTrueClient.withPkce`, a subclass over a protected field), not for the client: with `flowType: 'pkce'` set for good, `signUp` would leave a verifier in storage and break the existing "one key" tests. (2) auth-js 2.117 also writes per-flow verifier slots and an index that our exchange (no flow id in the URL) never removes; they would stay in web storage, against c13. `withoutVerifierSlots` drops those writes; the fixed `<key>-code-verifier` does the work and the exchange removes it. Checked end to end with the real SDK: after start only `nestly-auth-code-verifier`; after return only `nestly-auth`. (3) Optional `completeGoogleSignIn` on the session source's `auth` dep (`Partial<Pick<...>>`) so existing fakes of `AuthSessionPort` still typecheck. (4) The clear list also holds `given_name`, `family_name` (Google profile claims); `locale` and `email` are not touched.
**Deviations**      none. Answer to the SPEC CHALLENGE question: `POST /api/register` takes the email from neither the token nor the body (the body has no email field, the route reads only the identity's user id) — c10 "not sent" holds with no work.
**Deliberately not done**   Welcome/Login/Register buttons, the navigation adapter, flow file (P3). Completion step 2, password, `updateUser({password})` (P2b). Rule L. No story for the new feature (no new `components/` piece).
**Uncertain**       Whether Supabase narrows scopes to `openid email` (DR-3 default applies; `profile` would be ignored and c12 still clears). Whether a repeat Google sign-in re-fills the metadata keys: the clear runs on every return, so it holds either way. The `flowType` toggle relies on auth-js reading `flowType` only inside `signInWithOAuth` and the exchange (checked in 2.117.3); an SDK upgrade must re-check it.
**For TEST ENGINEER (FINDING)**   `tests/google/google-return.test.tsx` seeds the verifier as a raw string. auth-js writes and reads it as JSON (`getItemAsync` returns null for a non-JSON value), so every success path (14 tests) fails with `pkce_code_verifier_not_found`. Fix: seed `JSON.stringify(VERIFIER)`. I confirmed it by temporarily wrapping the read in product code: all 41 tests in `tests/google` passed, then I reverted the wrap. Not edited by me.
**Preview path**    The Welcome "המשך עם Google" button still links to `/auth/google` bare: it now shows the failure text with links to login and register (expected until P3). Return URLs to try on the Preview: `/auth/google?error=access_denied` (cancel text), `/auth/google?error=server_error` and `/auth/google?code=x` (failure text; URL ends bare). A real Google round trip needs P3 and Afik's Supabase/Google setup.
**Neighbouring**    none

## P2b — completion for a Google user: password, consent, order (criteria 7-11)

**Approach**        New `features/registration/RegisterGoogleCompletionStep.tsx`: step 2 for a Google user = email as read-only text (no input), password (`PasswordInput`, VAL-003 via `validatePassword` in `step2-form.ts`, same text), `ConsentField`, final action "יצירת החשבון" with native `disabled` until password valid and consent ticked. Submit: `account.setPassword` (Auth `updateUser({ password })`) first; on failure register is not sent, generic text, password field cleared, everything else kept; on success `getAccessToken` then the existing `registerAccount` (body unchanged, no password). Register failure keeps the password and the consent; retry runs `setPassword` again. Ports: `GoogleAuthPort.readGoogleAccount()` (Auth `getUser()`: provider `google` and email, else null; rejects when Auth cannot answer) and `setPassword()`; `SessionAccount.googleAccount()` / `setPassword()` over them (optional on the source's `auth` dep, like `completeGoogleSignIn`). `RegisterPage` asks `googleAccount()` once per completion and hands `RegistrationFlow` a `GoogleLookup`; `RegisterConsentStep` and the email+password orphan path are untouched. Criterion 11 needs no code: `decideAccess` already sends `signed-in-no-account` to `/register` on reload (tests extend it).
**Decisions**       (1) Google-vs-orphan is decided by Auth's user (`app_metadata.provider === 'google'`), not by a client flag, so a reload mid-completion still asks for the password. The provider stays `google` after the first password is added. (2) Fail closed: step 2 waits (`GoogleLookupHold`, "רגע אחד") until the answer is in; a failed read shows the retry text and a retry button, never the password-less consent step. (3) `same_password` is a success on every call, not only on a retry: Auth says the password already is the typed one. Slightly wider than criterion 9 and never worse. (4) A refused `updateUser` (including a weak-password refusal) shows the generic text, as the spec says; no per-code text.
**Deviations**      none (see decision 3).
**Deliberately not done**   Per-error copy for `updateUser` failures; a story for the new screens (feature code, not `components/`); Welcome/Login/Register buttons and flow file (P3).
**Uncertain**       `getUser()` is one extra Auth request when the completion page opens; it also validates the token with Auth, and auth-js may end the session if Auth answers that the token is invalid, which then reads as an ended session. The "reauthentication needed" refusal (session older than 24 h) is not handled specially: it shows the generic text and the user can sign out and in again.
**Preview path**    Needs P3 and Afik's Supabase/Google setup for a real round trip. Without them: nothing new is reachable except that an email+password orphan still sees the consent-only step 2 (unchanged).
**Neighbouring**    none

## P3 — the "המשך עם Google" button and the return screen (criteria 16-18)

**Approach**        `components/shared/google-button.tsx` (+ stories, `shared/google-button: 3` in `tools/check-stories.mjs`): a soft `lg` block `Button` (native `<button type=button>`), `disabled` + `pending` (aria-busy, loader) while busy, an `InlineAlert` (role=alert) above it on failure, an sr-only `role=status` line while busy. State in `hooks/use-google-sign-in.ts` (ref guard: a double press starts one `start()`; stays busy after `'left'`; on failure re-enabled, text shown, focus returned to the button). The action is `services/auth/google-sign-in.ts` `createGoogleSignIn` (Auth's `startGoogleSignIn(redirectTo)`, then `leave(url)` only for an https URL, or http on localhost) and `platform/browser-navigation.ts` (`window.location.assign`, the one place that navigates away). `App.tsx` wires the real one (`redirectTo` = origin + `/auth/google`) into `GoogleSignInContext`; `App` takes an optional `googleSignIn` prop for tests. Placed: Welcome (second action, where the link was), Login (after "התחברות"), Register step 1 only when not in completion. `GOOGLE_FAILED_TEXT` moved to `lib/auth-texts.ts` (a Feature may not import a Feature); the inline failure is that same text (criterion 3). The return screen (heading, `role=alert`, focus on the heading, no placeholder title) was already built in P2a; I changed nothing there but the import.
**Decisions**       (1) The default `GoogleSignInContext` cannot start: a screen with no wiring (stories, tests) shows the failure text and never navigates, same as the Auth port's not-configured default. (2) Native `disabled` as the spec says; a disabled button drops focus, so focus is put back on it after a failure. (3) Status line copy "עוברים אל Google" is new copy, not in the spec.
**Deviations**      Spec criterion 7 names the final action "יצירת החשבון"; P2b built, and F1.5's consent step has, "יצירת חשבון" — I left product copy as P2b built it. The flow file and TEST ENGINEER's tests should assert whichever ORCHESTRATOR settles on; one-word change in `RegisterGoogleCompletionStep.tsx` if the spec wins.
**Deliberately not done**   No Google logo (out of scope). No handling of a page restored from the back/forward cache while busy: it would show the button busy until reload (`pageshow` is not handled). Flow file (TEST ENGINEER). No axe run by me beyond the existing unit suite (jsdom); axe at 375/1280 and the 44px target (`min-h-13` from `size="lg"`) are for the flow/CI.
**Uncertain**       The back-button case above is the likeliest visible rough edge on the Preview. The alert sits above the button in the actions column, pushing the other actions down; fine at 375x812 for Welcome, not seen on a device.
**Screenshot baselines**   Yes: Playwright baselines of the stories `pages/WelcomePage`, the Login form and `features/registration/RegisterStepOne` change (a new button), and `shared/GoogleButton` is new. ORCHESTRATOR runs `update-baselines`.

Without it: open `/`, `/login`, `/register`; the button is there; press it: with the Supabase env vars set the browser goes to the Auth authorize URL (Google's page if the provider is on; an Auth error page if not), with them unset the inline failure text shows and nothing navigates. Return URLs as in P2a.
