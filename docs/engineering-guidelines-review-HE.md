# סקירת הנחיות הנדסיות חיצוניות: מה מתאים ל-Nestly

**תאריך:** 10.10.2026
**מקור:** חבילת `engineering-guidelines-2026-10-10.zip`, חמישה קבצים שנכתבו למוצר אחר (Neogenic, שנבנה מעל Vibey) ולעבודה עם Codex ו-Cursor. החבילה לא הועתקה לפרויקט. המסמך מנסח את הדברים במילים שלנו ולא מצטט אותה.
**סטטוס:** אפיק החליט ב-10.10.2026 ליישם לפי ההמלצות. מה יושם ואיפה: סעיפים 5 עד 7. הרשומה ב-`decisions.md` נושאת את אותו תאריך.

**מה נשמר בלי שינוי, לבקשת אפיק:**
- שפות הפיתוח: React, JavaScript, CSS ו-HTML.
- סדר הבנייה: קודם Web, ורק אחריו אפליקציה ב-React Native.
- שני השערים האנושיים ושלושת הכללים ששומרים על עצמאות הביקורת.
- העיקרון שההחלטות של אפיק.

## 1. אפיון החבילה

### `AGENTS.md`: פרוטוקול העבודה של Codex ב-Neogenic

השכבה החדשה, והיא גוברת על שאר הקבצים. Neogenic הוא מוצר למרפאות, עם מידע רפואי ורגולציה.

| נושא | מה הוא קובע |
|---|---|
| עבודה מקבילית | כמה sessions של Codex במקביל. כל אחד עובד בענף וב-worktree משלו, וכל שינוי משותף מקבל כותב אחד. session מתאם (F1) מחזיק את תור השינויים, ו-session אחר אחראי על התשתית |
| לוח משימות | כל משימה היא כרטיס עם מזהה, בעלים, sprint וסטטוס. "בלי כרטיס אין עבודה". כרטיס ממתין חייב לומר למה הוא ממתין |
| sessions ישנים | session שלא מופיע ברשימה הוא בדרך כלל רק לא פעיל. מעירים אותו בהודעה לפני שמכריזים שהוא סגור. הרצה ארוכה מקבלת "שומר" שמעיר את ה-session כשהיא מסתיימת |

נכתבו במקור ל-Cursor ול-Claude. ב-Neogenic הם נשארו בתוקף, חוץ מחלקים שהוגדרו כ"היסטוריים".

### אופי החבילה

- **שתי שכבות שגוברות זו על זו.** השכבה החדשה מכריזה על חלקים מהישנה כהיסטוריים, וכל קורא צריך לפענח מה עדיין בתוקף.
- **הרבה הדגשה:** "CRITICAL", "MANDATORY", צ'קליסטים ארוכים. פרקים שלמים מופיעים כמעט מילה במילה בשני קבצים.
- **סתירות פנימיות.** מפורטות בסעיף 9.

## 2. אפיון Nestly, לפני הסקירה

- **צוות:** ORCHESTRATOR בלולאה הראשית, ושבעה subagents: SPEC, DATA ARCHITECT, ALGORITHM & DATA, BUILDER, SCOUT, CRITIC ו-TEST ENGINEER.
- **צינור:** שלושה מסלולים (Light, Standard, Elevated) ושני שערים אנושיים: אישור ה-spec ולחיצה על ה-Preview.
- **שלושה כללים ששומרים על הביקורת עצמאית:**
  - CRITIC לא קורא את `notes.md`.
  - TEST ENGINEER לא רואה את ה-diff.
  - קריטריון שאי אפשר לבדוק בטסט אינו קריטריון.
- **למידה:** `escapes.md` ו-`noise.md`, תקציב בדיקות לכל סוכן, ותקופת ניסיון של חמישה פיצ'רים לכל שינוי.
- **ידע:** `conventions.md`, `data-model.md`, `srs-review-points.md` ו-`ai-ml-readiness.md`.
- **מקור אמת:** ה-SRS ב-markdown, גרסה 2.5 לפני הסקירה, עם כלי אינדקס וייצוא ל-Word.
- **Stack:**
  - React ו-JavaScript בלבד, בלי TypeScript, ולכן בלי בדיקת טיפוסים בזמן קומפילציה.
  - Tailwind.
  - Supabase עם RLS. הלקוח מדבר ישירות עם המסד, ו-Edge Functions משמשות רק כשנדרש סוד.
- **מצב:** CI ו-hook אושרו ועוד לא נבנו. אין עדיין קוד.

## 3. הבדלי יסוד: למה אי אפשר להעתיק

| | Vibey / Neogenic | Nestly |
|---|---|---|
| כלי | Codex ו-Cursor, כמה sessions במקביל | Claude Code: לולאה ראשית ו-subagents |
| שפה | TypeScript, עם Zod כמקור לטיפוסים | JavaScript בלבד (iron rule) |
| שרת | API routes של Next.js ו-NestJS עם שלוש שכבות | אין שרת אפליקציה: Supabase ישירות, ו-Edge Functions כשנדרש סוד |
| אכיפה | בעיקר טקסט וצ'קליסטים | כלל 1: מה שחשוב נאכף ב-hooks וב-CI |
| צוות | כמה תחומי אחריות במקביל, עם מתאם | מייסד יחיד, בלי מקביליות בתוך פיצ'ר |
| שכבות הרשאה | admin כדגל role | Admin, ו-Moderator עם Permission Keys, ושלוש-עשרה שכבות הרשאה |

**המשמעות:** כמעט כל כלל אצלם צריך תרגום לארכיטקטורה שלנו. למשל, אצלם "כל קריאה עוברת דרך API route". אצלנו המקבילה היא שהקריאה עוברת דרך שכבת service, ושה-RLS הוא השער.

## 8. נדחה, ולמה

- **לוח משימות, כרטיסים, sprints, מתאם ו-sessions שמעירים זה את זה.** אלה פותרים בעיה של כמה sessions במקביל, ואצלנו אין מקביליות כזו. WORKPLAN ו-`.work/` עושים את העבודה.
- **changelog לכל שינוי.** זה היה מקור רביעי לאותו מידע.
- **"תמיד לקרוא הכול".** זה שורף קונטקסט שהעבודה עצמה צריכה. אימצנו גרסה מצומצמת (A3).
- **API routes, NestJS, guards, throttler, CORS ו-allowlist ב-Express.** אלה שייכים לארכיטקטורה שאין לנו.
- **barrels בכל תיקייה.** עוד מקום שצריך לזכור לעדכן, ובלי typecheck טעות בו מתגלה רק בזמן ריצה.
- **TypeScript, LangGraph, OpenRouter, חבילת templates ו-monorepo.** חלק אסורים לפי ה-iron rule, וחלק לא רלוונטיים.
- **סגנון ההדגשה והצ'קליסטים הארוכים.** תקציבי הבדיקות ב-`learning.md` קיימים בדיוק נגד זה.

## 9. לקחים על כתיבת הנחיות לסוכנים

**הסתירות שמצאנו בחבילה:**
- **הסתרת שגיאות.** הכלל אומר להחזיר הודעה כללית, ושתי דוגמאות קוד מחזירות ללקוח את `error.message`.
- **rate limit.** כתוב "לכל route", וגם "לא לייבא רכיבי אבטחה ל-GET פשוט".
- **RLS בלבד.** אבל דוגמת הטרנזקציה כתובה כ-SECURITY DEFINER, ועוקפת אותו.
- **לוגים.** דוגמת הלוג רושמת את כל הקלט. במוצר שלנו זה היה מכניס מידע על הריון וילדים ללוג.
- **כפילויות.** פרקים שלמים כתובים פעמיים, ובמקרה אחד אותה תבנית מופיעה פעמיים באותו קובץ.

**הלקח: סוכן מעתיק דוגמה מהר יותר משהוא מקיים כלל.** דוגמה שסותרת את הכלל מנצחת אותו. אצלנו כבר בנויים שלושה מנגנונים נגד זה:
1. כל כלל כתוב במקום אחד.
2. סדר העדיפויות מוגדר: ה-SRS גובר על knowledge, ו-`workflow.md` גובר על הגדרות הסוכנים.
3. הדוגמאות ב-`conventions.md` מפנות לקוד אמיתי שכבר עבר ביקורת.
